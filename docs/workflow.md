# 工作流与变更评审

> 给谁看：所有人。这份文档回答"接到一个任务，我应该怎么走完，怎么改 Spec 不翻车"。

## 全景

```text
接到任务 → 读该读的 Spec → 没有缺口就实现；有缺口先补 Spec
        → 实现 + 测试 → 执行前后自查 → PR 评审 → 合并，成为新约定
        → 上线后的数据/事故/反馈成为下一轮变更的来源（闭环）
```

一个普通需求通常只经过三步：需求与验收标准 → 受影响的专业 Spec → 代码与测试。规模越大，越值得先写清楚再动手；规模越小，Spec 和代码在同一个 PR 里走完。

## 开始任务前

1. 读仓库根目录的 `AGENTS.md` 和 `spec/CONVENTIONS.md`；
2. 确认自己在这次任务里的角色；
3. 按 [角色阅读边界](roles.md) 读该读的 Spec，以及任务直接引用的上游 Spec；
4. 检查需求、设计、架构、接口、数据和测试之间有没有缺口或冲突。

**不需要通读整个 Spec 树。** `spec-map.yml` 把代码路径映射到 Spec，角色清单决定展开哪些目录——每个执行者拿到的是"你这次任务需要的文件清单"，不是一本书。

## 发现 Spec 不完整或冲突：不要绕过

代码里"绕过去"是最贵的决策——三个月后没人记得当时为什么绕。正确的做法按影响范围分三档：

| 影响范围 | 做法 |
|---|---|
| 小改动（措辞、边界澄清、单文件） | 在**同一个 PR** 里同步修改 Spec、代码和测试，一起评审 |
| 复杂改动（跨角色、含迁移或兼容性风险） | 先创建 `changes/CHANGE-xxx/`，写清动机、范围、影响、兼容性、回滚和任务，评审通过再动手 |
| 破坏性公共契约 | 必须让所有受影响消费者在**同一评审链路**里确认，不允许悄悄改 |

Change 是评审说明，不是另一份 Spec 真相——Git 分支和 PR diff 已经隔离了"当前版本"和"提议版本"，不再维护一份 delta 副本（两份真相必然漂移）。

**Spec 还没评审通过，就不能当现行约定用。** 团队可以选：Spec 和代码同一个 PR 评审；或者要求先合 Spec PR，再开始实现。

## AI 执行前自查

- 我读到的 Spec 覆盖当前角色和任务吗？哪些条款直接约束这次修改？
- 哪些原生契约文件会变？文档之间有没有矛盾？
- 发现缺口时，是否先提 Spec 变更而不是埋头写代码？

## AI 执行后自查

- 修改符合需求、设计、架构和专业契约吗？
- API、数据、设计资源和测试需要同步更新吗？
- 有没有新增任何 Spec 没描述过的**公共行为**？
- 相关测试覆盖验收标准吗？
- 真实跑过 lint、测试、迁移检查和构建吗（不是"应该能跑"）？

报告固定四件套：**用了哪些 Spec ID、改了哪些文件、发现的偏差、执行了哪些命令**。

## PR 评审：各看各的

评审者不需要逐字审所有文档，只检查自己负责的事实：

1. **Product**：需求表达了正确的业务行为和边界吗？
2. **Design/Architect**：受影响的专业契约一起更新了吗？
3. **Engineering**：代码和测试与契约一致吗？
4. **QA/PM**：兼容性、迁移、发布风险有未决项吗？

合并后，PR 里的 Spec 就是新的当前约定；实现与否由测试、CI 和发布记录证明。提交信息按 `CONVENTIONS.md` 的格式写（`type(scope): 说明`，涉及 Spec 变更必须带 spec id）。

## 合并之后：闭环

上线不是终点。**运行期的数据（使用率、错误率、耗时）、事故和用户反馈，是下一轮 Spec 变更的最高优先级来源**——修一个 Spec 规则，常常比写十个新功能更值钱。反馈走同一套流程：先改 Spec（小改动直接 PR，跨角色走 Change 提案），再改实现。

一个完整例子（含测试如何验证 Spec）见 [示例走查](../examples/todo-due-date/WALKTHROUGH.md)。
